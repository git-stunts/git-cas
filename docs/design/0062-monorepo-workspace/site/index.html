A guided tour, from zero

Binaries that travel with the repository.

git-cas stores large files inside Git's own object database, chunked, verified and optionally encrypted. This page teaches how it works, how it is built, and the plan to split it into a workspace of packages.

Chapter 1 · In sixty seconds

The whole idea, compressed

Git already has a world-class, replicated, content-addressed blob store: its object database. git-cas uses it to hold big files, so artifacts replicate wherever the repository does. Stop here and you have the gist; keep going and you will be able to explain every box below.

2

Chapter 2 · The problem

Source code is everywhere. The binaries are not.

Every clone of a repository is a full copy of its history. That replication is why Git survives outages and censorship. Large artifacts break the pattern: they sit on one hosting endpoint, and a repository full of mirrors still depends on a single server for its binaries.

Code replicates by default

Six machines hold the brand-kit repository: Ada's laptop, the origin, two mirrors, a CI runner, an offline archive. Any of them can rebuild the full history for the others. Delete any one and nothing is lost.

Binaries live somewhere else

The 12 MiB hero.psd is too big for comfortable Git history, so the team parks it on an artifact host and commits a pointer. Every machine now has a dashed dependency on one endpoint that is not part of the repository at all.

The endpoint goes away

Blocked network, expired bucket, vendor shutdown. The code still replicates, but every pointer dangles. The mirrors are complete and useless at the same time.

Intuition to carry forwardIf the artifact were made of ordinary Git objects, it would already be on all six machines.

Chapter 3 · The running example

Meet hero.psd

Every chapter from here on follows one file through the system. Ada, a designer on the brand team, needs the hero artwork in the brand-kit repository. 12,582,912 bytes, a layered Photoshop file, re-exported a few times a week with small edits. Two foils draw the edges: a 3 KB logo.svg, and a deliberately corrupted blob later on.

The first four bytes, 38 42 50 53, spell 8BPS: the Photoshop signature. Everything after it is pixels, layers and masks. To Git, and to git-cas, none of that structure matters. The file is a sequence of bytes, and bytes can be cut, named and stored.

Two things make this file a good teacher. It is big enough that storing it whole in Git history would hurt (every edit would add another 12 MiB to every clone forever). And Ada's edits are small: a color tweak changes a few hundred kilobytes in the middle of the file, leaving the rest byte-identical.

The foillogo.svg is 3 KB. It fits in one chunk, so chunking buys it nothing. It still gets a hash-derived name, a manifest and the same integrity check. The machinery is the same; only the payoff differs.

Chapter 4 · Content addressing

Name things by what they contain

A hash function turns any bytes into a fixed-size fingerprint. SHA-256 produces 32 bytes, and changing a single input bit changes the fingerprint beyond recognition. Content-addressed storage uses the fingerprint as the name. Same bytes, same name. Different bytes, different name. Git has worked this way since 2005.

Try it

The board computes a real SHA-256 in your browser (crypto.subtle.digest). The 32 bytes are drawn as a grid of 32 tiles, each colored by its value, and printed as 64 hex characters. Edit the text and watch the whole grid churn.

One byte, every tile

This step appends one character to the sample. Not one tile survives. That avalanche is what makes a hash safe to use as a name: you cannot find two different files that share one, so the name is a proof of the content.

Git already does this

Every Git blob is named by a hash of its bytes (SHA-1 in most repositories today, SHA-256 in newer ones). git-cas leans on that for storage, and additionally records a SHA-256 digest of every chunk in its own manifest, so integrity does not depend on which hash the repository happens to use.

Intuition to carry forwardA hash-named object can be verified by anyone who holds it. No trust in the sender is required.

Chapter 5 · Chunking

Cut the file so that small edits stay small

Storing hero.psd as one 12 MiB object means every edit stores another 12 MiB. Cutting it into pieces lets unchanged pieces be reused. Where you cut decides how much gets reused. git-cas offers fixed-size cuts (predictable) and content-defined cuts (shift-resistant), and defaults to a 256 KiB target.

Fixed-size chunks

Cut every 256 KiB. The top track shows the file as a strip; each colored segment is a chunk, and its color comes from a hash of its contents. Simple, and fine when edits replace bytes in place.

Insert a few bytes at the front

Ada's export adds a metadata header. Drag the slider on the board. With fixed cuts, everything after the insertion shifts, so every boundary lands on different bytes and every chunk gets a new hash. One small edit, a whole new file in storage.

Content-defined chunking

The bottom track cuts where a rolling hash of the last few bytes hits a pattern (git-cas uses Buzhash with FastCDC-style normalization: a strict mask below the target size, a looser one above it). Boundaries are properties of the bytes themselves, so they move with the content. Only the first chunk changes; the rest keep their names.

Intuition to carry forwardContent-defined boundaries make deduplication survive insertions. That is what makes versioned binaries cheap.

Chapter 6 · Chunks become blobs

Two versions, one pool of blobs

Each chunk is written to Git as a blob object, which Git names by hash. If a chunk already exists, Git simply does not write it again. Deduplication is not a feature git-cas adds; it falls out of using a content-addressed store.

Version 1 is stored

The top row is the first twelve chunks of hero.psd as Ada first exported it. Each points at a blob in the object database below. Twelve chunks, twelve blobs.

Version 2 arrives

Ada changes the sky gradient. With content-defined chunking, only chunk 6 has different bytes. The bottom row is version 2: eleven chunks have the same hash as before, one is new.

Same hash, same blob

Version 2's chunks resolve to the blobs that already exist. Git writes exactly one new object. Both manifests are complete, both files can be restored, and the shared blobs are stored once.

The accounting

Two 3 MiB prefixes, 6 MiB of logical content, 3.25 MiB stored. Across the full 12 MiB file and a week of exports, the ratio is what keeps the repository small. Later, encryption will threaten this property and convergent mode will rescue it.

Chapter 7 · The manifest

The recipe that rebuilds the file

Blobs alone are a bag of pieces. The manifest is the ordered list that says which pieces, in which order, with which fingerprints. It is itself stored as a Git blob, so it gets the same replication and the same hash-derived name as everything else.

Ordered chunk entries

Each entry carries its position (index), size, SHA-256 digest and the Git object id of the blob that holds it. The chunking block records how the cuts were made so a reader can reason about them later.

A fingerprint of the recipe

The manifest carries its own integrity hash and the version of the format that wrote it. A tampered or truncated manifest is detected before any chunk is fetched. Field names on the board are abridged; the real schema lives in ManifestSchema.js and is exported as @git-stunts/git-cas/schema.

When the list gets long

Above 1,000 chunks (the merkleThreshold) the flat list becomes a tree: sub-manifests, each a blob, referenced by object id. Readers walk the tree and fetch only the branches they need. The same trick Git plays with trees of trees.

Chapter 8 · Restore and verify

Rebuild the bytes, trust nothing

Restoring is the manifest read in reverse: fetch each blob, check its SHA-256 against the recorded digest, append it to the output. A chunk that fails verification stops the restore with an INTEGRITY_ERROR; there is no option to skip it. Chunks are fetched in parallel through a bounded window so large files stream without buffering everything.

Read the recipe

The manifest on the left lists twelve entries. Nothing has been fetched yet; the restore knows exactly what it needs and how big the result will be.

Fetch through a window

A prefetch window keeps four fetches in flight (PrefetchWindow). Blobs arrive out of order; the window hands them to the writer in manifest order. Memory stays bounded by the window, not by the file.

Verify every chunk

Each blob is hashed and compared with the manifest's digest. Press Corrupt blob 7 on the board to flip one byte in storage, then scroll back and forth. The restore halts at the bad chunk and names it.

Assembled

Twelve verified chunks written in order reproduce hero.psd byte for byte. The whole-file digest in the manifest is checked last. Only then does the restore report success.

The second foilA corrupted blob is the thing that must not restore. The failure is loud by design.

Chapter 9 · Encryption

Envelopes, recipients and a trick to keep dedup

Anyone who can read the repository can read its blobs. For secrets, git-cas encrypts chunks with AES-256-GCM. The data key never touches the repository in the clear; it is wrapped once per recipient, so a team can share one asset without sharing one passphrase.

One data key

A random 256-bit data encryption key (DEK) encrypts the chunks. Each ciphertext also binds the asset's slug as authenticated data, so a blob cannot be swapped into a different manifest without the check failing.

Recipients wrap the key

Ada's passphrase goes through scrypt to produce a key-encryption key (KEK), and the DEK is encrypted under it. The CI runner has a key file; same wrap, different KEK. The manifest stores one wrappedDek per recipient, each 32 bytes plus a nonce and tag. Press Add recipient to let Bo in.

Rotate without re-encrypting

Ada changes her passphrase. Only her wrapped copy of the DEK is rewritten; the blobs are untouched. Press Rotate Ada's passphrase and watch what flashes and what does not. A vault-wide rotation is the same operation across every manifest.

Convergent mode

Random keys destroy deduplication: the same plaintext chunk encrypts to different bytes each time. In convergent mode the per-chunk key and nonce are derived from the chunk's own content hash under the master key. Identical plaintext gives identical ciphertext, so Git deduplicates encrypted chunks too. The cost is well known: an attacker who already holds a plaintext chunk can confirm you stored it. framed and whole modes avoid that at the price of dedup.

Chapter 10 · Keeping things alive

Git deletes what nothing points to

Git's garbage collector keeps an object only if some ref leads to it. Blobs written by git-cas are no exception. So git-cas never relies on loose objects: every manifest and chunk is anchored under a ref, and lifecycles are expressed as which refs point where.

Unreachable means gone

Here are the objects for hero.psd and logo.svg: manifests and chunk blobs. Nothing points at them. On the next git gc they are swept. This is correct Git behavior and the reason a naive "just write blobs" approach loses data.

The vault ref

git-cas keeps a named index at refs/cas/vault: a commit whose tree maps slugs like brand/hero to manifests. Now every chunk is reachable through ref → commit → tree → manifest → blob, and GC leaves it alone.

Remove an entry

Press Remove hero.psd. The vault tree no longer references its manifest, so the manifest and the blobs only it used become collectible. The blob shared with logo.svg stays, because something still reaches it. Reachability does the bookkeeping for us.

Root sets: retention without history

The vault keeps history, which is right for named assets and wrong for caches. refs/cas/rootsets/* point at parentless commits replaced with compare-and-swap. Remove an entry and its objects become collectible immediately; no old generation keeps them alive. Caches, expiring sets and workspaces are all built on this.

Intuition to carry forwardIn git-cas, "retained" means "reachable from a ref we manage". Every higher-level feature is a policy about refs.

Chapter 11 · Above the core

Six ref namespaces, six lifecycles

Everything so far is the storage core. Applications need more than "store a file": they need named assets, caches that expire, replay markers that cannot be shortened, and structured bundles retained atomically. git-cas expresses each as its own ref namespace with its own rules. The downstream consumer that drove most of them is git-warp, a graph database that keeps its materializations in git-cas.

refs/cas/vault

Named, versioned assets. Slug → manifest, with history, optional privacy mode that HMAC-masks slug names, and passphrase rotation across the whole vault. This is what the CLI's store --slug and restore talk to.

refs/cas/rootsets/*

The retention kernel from the last chapter. A root set is a mutable set of entries anchored by a parentless commit. It exists so the three namespaces below do not each invent their own GC story.

refs/cas/caches/*

Managed cache sets: TTL, entry and byte limits, approximate LRU eviction, repair. A cache hit can be acquired, which pins its generation under refs/cas/cache-acquisitions/* while the caller uses it, then released.

refs/cas/expiring/*

Replay markers for security-sensitive flows: add-if-absent, digest-only metadata, and release only by expiry. There is deliberately no remove, no capacity limit, nothing that could shorten a marker's life.

refs/cas/workspaces/* and application handles

Assets, immutable pages and ordered bundles are addressed by opaque handles rather than raw object ids. A staging workspace admits a batch of dependent writes and retains the result under one exact generation, so a consumer never sees half of a structure.

Chapter 12 · Replication

Back to the six machines

Because everything is Git objects under Git refs, the ordinary verbs move it: push, fetch, clone, bundle. No server-side plugin, no second protocol. This chapter replays the problem from Chapter 2 with hero.psd stored the git-cas way.

Ada pushes

Her laptop pushes refs/cas/vault along with the branches. The manifest and 48 chunk blobs ride in the same pack as her commits.

Mirrors fetch

The EU mirror, the CI runner and the offline archive fetch as they always did. Each now holds every byte of hero.psd, verified by Git's own object hashing on the way in.

The origin disappears

Same outage as before. This time the dashed dependency has nothing to break. CI restores from the EU mirror; the archive restores with no network at all.

What changed

Not the network, not the hosts. Only where the bytes live. That is the whole thesis of the project, and the rest of this page is about keeping the code that delivers it healthy.

Chapter 13 · How it is built

A core that has never heard of Node

git-cas runs on Node.js 22+, Bun and Deno from one codebase. It manages that with a hexagonal architecture: the domain speaks only to abstract ports, and runtime-specific adapters plug into them. A test guards it: no file under src/domain may import node:, touch Buffer or process, or use Node streams. The grep for domain-to-infrastructure imports returns nothing.

The domain

CasService orchestrates store and restore strategies, the chunk repository, manifests, key resolution and integrity checks. It works on Uint8Array and async iterables, nothing platform-specific. 10,900 lines including the ports and adapters that ship with it.

The ports

Six contracts: CryptoPort, GitPersistencePort, GitRefPort, CodecPort, ChunkingPort, CompressionPort, plus ObservabilityPort for logs and metrics. The domain depends on these interfaces and nothing else.

The adapters

Pick a runtime on the board. Node uses node:crypto; Bun has its own adapter; Deno gets WebCrypto. Git itself is reached through @git-stunts/plumbing, which shells out to the git binary and keeps long-lived cat-file and mktree sessions open. The domain does not change when you switch.

Chapter 14 · Today's shape

One package, 38,808 lines, four surprises in the dependency tree

All of this ships as a single npm package, @git-stunts/git-cas@6.5.10. The library is 26,479 lines; the bin/ directory adds 12,329 more for a human CLI, a machine-facing agent CLI and a full-screen terminal dashboard. The problem is what rides along.

Everything in one circle

Each bubble is a cluster of source files, sized by line count. The clusters are already clean: the import graph between them has no cycles and only two edges that point sideways. The boundaries exist in the code; they just do not exist in the package.

A third of it is terminal UI and CLI

The dashboard alone is 6,238 lines. It shares a package, a test runner, a release cadence and a files list with the storage engine. Changing a keybinding and changing the restore pipeline are the same kind of release.

The library ships a TUI framework

Four @flyingrobots/bijou* packages are runtime dependencies. Anyone who installs @git-stunts/git-cas to store files also installs a terminal rendering stack they never call. One of the four, bijou-tui-app, is declared and never imported anywhere.

Intuition to carry forwardThe code already has seams. The split moves package boundaries onto seams that exist.

Chapter 15 · The plan

A workspace of fifteen packages, one version

Turn the repository into a pnpm workspace. Thirteen published packages and two private ones, all sharing one version number, one tag, one changelog and one release job. The umbrella package keeps today's API, so existing consumers change a version range and nothing else. Hover a node to see what moves into it; click one to see what it depends on.

Layer 0: the core

git-cas-core is Chapters 4 through 9: chunking, manifests, strategies, encryption, the ports, and the adapters for Git, crypto and codecs. It depends on @git-stunts/plumbing and nothing from the rest of the workspace.

Layers 1 to 3: the lifecycles

Chapters 10 and 11 become packages: vault and rootsets directly on core; bundles on rootsets; cache, expire and workspaces on bundles; doctor on all of them. The graph is a DAG, and pnpm's isolated node_modules turns any undeclared edge into a runtime error.

Layer 4: the umbrella

@git-stunts/git-cas shrinks to a composition root and a re-export list, about 400 lines. Its three entrypoints are unchanged. git-warp imports it in 105 places and needs no edit beyond ^7.0.0.

The apps, and lock step

agent is the headless command executor; cli, tui and a new mcp server are three transports over it. The binary moves out of the library, which is the one breaking change and the reason this is v7.0.0. Watch the version badges: they move together, always.

Chapter 16 · How we get there

Eleven slices, each a green pull request

The split is not one big-bang commit. Every slice is one PR against main that passes lint, 2,194 unit tests, the Node/Bun/Deno Docker matrix and the release verifier before it merges. Apps come out first so the TUI work has a home; the domain is carved bottom-up underneath it.

Pre-flight no layout change

Remove the unused bijou-tui-app dependency, pin packageManager, move to vitest 3 projects, and relocate the fourteen documentation guard tests into a root test/repo/ suite so later moves update expectations once.

Workspace scaffold largest mechanical diff

Root becomes a private workspace; git mv the whole package into packages/git-cas/. Update Dockerfile, CI, hooks, verifier. Write the two RED tests first: every package shares one version, and every import resolves to a declared dependency.

Extract agent, cli, tui unblocks TUI work

Three app packages leave bin/. The umbrella drops its binary and the Bijou dependencies. A test installs the umbrella tarball and asserts no @flyingrobots/* package is present.

Chapter 20 · Cool ideas

What the split makes possible

Each of these is a candidate type:idea issue. Each names the package it would live in, which is the point: with boundaries in place, an idea has an address.

git-cas-testing

Publish the in-memory adapters

Memory persistence and ref adapters, deterministic crypto, a fake clock and fast-check arbitraries for manifests and handles. git-warp's suites spawn real git for things that only need the port contract.

git-cas-agent

One executor, four clients

CLI flags, JSONL, MCP tools and the TUI's Operations pane all call the same executor. A remote TUI over an SSH pipe becomes a transport change.

git-cas-mcp

Resources, not just tools

Expose git-cas://vault/<slug> and manifests as readable MCP resources, doctor as a tool, and a "diagnose this repository" prompt.

git-cas-cli · doctor

Sneakernet export

git-cas export --bundle wraps git bundle over refs/cas/*; import verifies every manifest before moving refs. Chapter 12 as a command.

git-cas-core · remote

Lazy chunk fetch

Clone with --filter=blob:none and fetch chunk blobs on demand from the promisor remote during restore. Answers the clone-size question with numbers.

new repository

A GitHub Action

Store build artifacts into refs/cas instead of actions/upload-artifact, so they travel with every mirror. Dogfood it in this repository's release job.

vault · rootsets · doctor

Signed generations

Sign vault and root-set commits with Git's SSH signing and verify in doctor. Provenance with no new infrastructure.

core · vault

Asymmetric recipients

X25519 envelope recipients beside passphrase-derived keys, so a team vault needs no shared secret. Bun and Deno support must be verified first.

git-cas-rootsets

defineCollection()

Cache sets and expiring sets are two instances of one Registry, Index, MetadataCodec and RootSet pattern. A kit lets a consumer define a lease set in a hundred lines.

git-cas-cli

Compiled binaries

bun build --compile and deno compile targets attached to each GitHub Release, for operators without a JavaScript runtime.

git-cas-schema

A wire-format spec

JSON Schemas generated from the Zod definitions for manifests, handles and the agent protocol, plus the one-page document a Rust or Go reader would need.

git-cas-tui · bench

Dedup preview

"What would storing this path save?" runs CDC over a directory, matches chunk hashes against the repository, and shows reuse before anything is written.
